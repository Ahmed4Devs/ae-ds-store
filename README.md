# متجر الوصل — متجر دروبشيبينغ AliExpress للسوق السعودي

متجر إلكتروني كامل مبني على **Next.js 16** يستخدم واجهات AliExpress Open Platform
(فئة `AE-Dropshipper`) طبقةَ توريد وتنفيذ خلفه، ومخصَّص للسوق السعودي.

---

## التقنيات

| المكوّن | الاختيار |
| --- | --- |
| الإطار | Next.js 16.3 (App Router · Turbopack · React 19.2) |
| اللغة | TypeScript |
| التنسيق | Tailwind CSS v4 |
| قاعدة البيانات | PostgreSQL عبر Prisma 7.10 (driver adapter) |
| المصادقة | better-auth |
| التحقق | zod |
| حالة الخادم على العميل | TanStack Query v5 |

## التشغيل السريع

```bash
npm install
cp .env.example .env          # ثم عدّل القيم
npm run db:deploy             # تطبيق الترحيلات
npm run db:seed               # حسابا مسؤول وعميل

المتجر على <http://localhost:3000>

| مسؤول | `admin@ae-ds-store.local` | `Admin12345` |

## وضعا التشغيل

المشروع يعمل بلا مفاتيح AliExpress. المتغيّر `AE_MODE` يحكم ذلك:

```bash
AE_MODE=mock   # بيانات وهمية مطابقة لبنية استجابات التوثيق (الافتراضي)
AE_MODE=live   # استدعاء الواجهات الحقيقية
```

الوضعان يمرّان بالمسار نفسه — التوقيع والتحقق وتصنيف الأخطاء والسجل —
فلا يفاجئك التبديل بسلوك مختلف. للانتقال إلى الإنتاج:

```bash
AE_MODE=live
AE_APP_KEY=...          # من لوحة تحكم AliExpress
AE_APP_SECRET=...
AE_ACCESS_TOKEN=...     # من حساب مشترٍ مفوَّض كحساب دروبشيبينغ
```

## طبقة جلب البيانات

النمط المعتمد هو **الجلب المسبق على الخادم ثم الترطيب على العميل**، وهو
ما توصي به TanStack لتطبيقات App Router:

```
مكوّن خادم  →  يجلب ويملأ QueryClient  →  dehydrate
                                              ↓
                                     HydrationBoundary
                                              ↓
مكوّن عميل  →  useQuery ببيانات جاهزة (بلا وميض تحميل)
                                              ↓
                          إعادة جلب · استقصاء · إبطال الذاكرة
```

### ما يُجلب على الخادم وما يُدار على العميل

| النوع | الطريقة | السبب |
| --- | --- | --- |
| محتوى الصفحة الأول | مكوّن خادم | لا شلال طلبات · الأسرار لا تغادر الخادم · أفضل لمحركات البحث |
| خيارات الشحن | `useQuery` | تتغيّر بتغيّر الكمية فتحتاج إعادة جلب |
| تتبّع الطلبية | `useQuery` + `refetchInterval` | AliExpress بلا إشعارات فورية |
| جدول الإدارة | `useQuery` + `refetchInterval` | رصد الطلبيات الفاشلة فور حدوثها |
| تعديلات السلة | `useMutation` + إجراء خادم | إبطال الذاكرة تلقائيًا بعد التعديل |

### عيبان صحّحهما هذا التحوّل

1. **أجرة الشحن كانت تُحسب لكمية واحدة فقط** على الخادم، فيبقى المبلغ
   المعروض خاطئًا عند تغيير الكمية. الآن مفتاح الاستعلام يتضمّن الكمية
   فيُعاد الحساب تلقائيًا.
2. **صفحة التتبع لم تكن تتحدّث** إلا بإعادة تحميل يدوية، رغم أن الاستقصاء
   هو السبيل الوحيد لرصد الحالة. الآن تُحدَّث كل دقيقتين وتتوقف عند
   الحالات النهائية.

### لماذا `fetch` لا axios

`fetch` مدمجة في المتصفّح وفي Node، وتتكامل مع طبقة التخزين المؤقت في
Next.js، ولا تضيف حجمًا. ما تقدّمه axios زيادةً (المهلة، رمي الخطأ تلقائيًا،
الاعتراض) مُغطّى في [`lib/query/fetcher.ts`](lib/query/fetcher.ts) بنحو
عشرين سطرًا.

### مسارات API

| المسار | الغرض | الحماية |
| --- | --- | --- |
| `GET /api/shipping` | خيارات الشحن لكمية محددة | تحقق zod من المدخلات |
| `GET /api/orders/[orderNumber]/tracking` | حالة الطلبية وتتبّعها | ملكية الطلبية |
| `GET /api/admin/orders` | طلبيات الإدارة وإحصاءاتها | دور ADMIN |
| `POST /api/payments/webhook` | إشعار بوابة الدفع | توقيع المزوّد بمقارنة ثابتة الزمن |
| `GET/POST /api/cron/sync-orders` | المزامنة الدورية | `CRON_SECRET` بمقارنة ثابتة الزمن |

كل مسار يتحقق من الصلاحية بنفسه لا اعتمادًا على التخطيط، لأن المسارات
قابلة للاستدعاء مباشرةً.

## قرارات تقنية أملاها التوثيق

هذه ليست اختيارات أسلوبية — كل واحدة تعالج سلوكًا موثّقًا في واجهات AliExpress:

### 1. الريال السعودي غير مدعوم إطلاقًا

فحصُ التوثيق كاملًا (200 واجهة) لا يُظهر `SAR` في أي قائمة عملات. لذلك:

- تُجلب الأسعار بالدولار وتُحوَّل محليًا
- سعر الصرف يشمل **هامشًا احتياطيًا** لتقلّب الصرف ورسوم التحويل
- سعر الصرف **يُثبَّت على الطلبية** وقت إنشائها، فلا تتغيّر الحسابات بأثر رجعي

### 2. `skuAttr` وليس `sku_id`

واجهة `ds.order.create` تتطلّب `sku_attr` بصيغته `73:175#Black Green;71:193#Polarized`،
بينما `logistics.buyer.freight.calculate` تقبل `sku_id`. الحقلان مخزّنان منفصلين،
والخلط بينهما يُفشل كل طلبية.

### 3. `order_list` مصفوفة

الطلبية الواحدة قد تنقسم إلى عدة طلبيات على AliExpress إن كانت المنتجات من بائعين
مختلفين. العلاقة في قاعدة البيانات **واحد إلى متعدد** بين `Order` و`AeOrder`.

### 4. `out_order_id` يُثبَّت قبل أي استدعاء

يُولَّد ويُحفظ محليًا قبل لمس المنصة. فإذا انقطع الاتصال ولم نعرف مصير الطلبية،
أعدنا الإرسال بالقيمة نفسها فترتد بـ `REPEATED_ORDER_ERROR` بدل الشراء مرتين.

### 5. تصنيف الأخطاء يحدد سلوك إعادة المحاولة

| الفئة | السلوك | أمثلة |
| --- | --- | --- |
| `RETRYABLE` | إعادة مباشرة | `ServiceUnavailable` · `TRACKING DATA NOT FOUND` |
| `REFRESH_THEN_RETRY` | تحديث البيانات ثم الإعادة | `INVENTORY_HOLD_ERROR` · `DELIVERY_METHOD_NOT_EXIST` |
| `INVALID_INPUT` | إصلاح المدخلات | أخطاء العنوان و CPF |
| `AUTH` | تجديد التفويض | `IllegalAccessToken` |
| `DUPLICATE` | ابحث ولا تُنشئ | `REPEATED_ORDER_ERROR` |
| `FATAL` | تدخّل بشري | `A001`–`A006` · `IncompleteSignature` |

خلط هذه الفئات في منطق واحد يُغرق النظام بمحاولات فاشلة أو يضاعف الشراء.

### 6. `logistics_service_name` من المصدر حرفيًا

يُؤخذ من `delivery_options[].code` ولا يُكتب يدويًا أبدًا، وإلا فالخطأ
`DELIVERY_METHOD_NOT_EXIST`.

### 7. احترام `ddpIncludeVATTax`

الضريبة تُحتسب على الشحن **فقط** حين لا يشمله السعر. تجاهل الحقل يعني
ازدواج الضريبة أو خسارتها.

### 8. لا إشعارات فورية

لا توفّر الواجهات webhooks، فالاستقصاء الدوري هو الخيار الوحيد. الفاصل الأدنى
عشر دقائق للطلبية الواحدة تفاديًا لاستنزاف حصة الاستدعاءات.

### 9. إعادة التحقق لحظة الشراء

الأسعار والمخزون يُعاد جلبهما من المصدر عند فتح السلة وعند الدفع — لا عند العرض.

### خصوصيات السوق السعودي

- **`nat_addr`** — العنوان الوطني، حقل خاص بالسعودية في التوثيق، بصيغة
  أربعة أحرف وأربعة أرقام (`RRDA2929`)
- تطبيع الجوال من خمس صيغ إلى الصيغة التي تتوقعها الواجهة
- المناطق محصورة في الثلاث عشرة منطقة الرسمية
- ضريبة القيمة المضافة 15٪
- التوقيت والتواريخ بتوقيت الرياض

## التحقق

```bash
npm run verify            # الكل (135 فحصًا)
# ثم مع خادم يعمل:
npm run verify:query      # 14 فحصًا إضافيًا

npm run verify:ae         # طبقة التكامل والتوقيع            (24)
npm run verify:pricing    # التسعير وقواعد السعودية          (24)
npm run verify:auth       # المصادقة                          (8)
npm run verify:orders     # دورة حياة الطلبية                (21)
npm run verify:payments   # الدفع والإلغاء                   (40)
npm run verify:store      # الصرف والنشر والتفويض والفاتورة  (28)
npm run verify:query      # مسارات API (يتطلّب خادمًا يعمل)  (14)
```

يتضمّن `verify:ae` مطابقة السلسلة الأساسية للتوقيع مع المثال الحرفي في
المستند 836، والتأكد من أن `skuAttr` يختلف عن `aeSkuId`، ومن ارتداد
`REPEATED_ORDER_ERROR` عند إعادة الإرسال.

وأهمّ ما في `verify:payments` ثلاثة فحوص تحرس المال مباشرةً: أن التوريد
**يُرفض** لطلبية غير مدفوعة، وأن إشعار الدفع المكرّر لا يُنشئ طلبية ثانية
لدى المنصة، وأن إشعارًا متأخّرًا يصل بعد الإلغاء لا يُحيي الطلبية ولا
يشتريها. ويتضمّن `verify:store` فكّ ترميز TLV والتأكد من أن خانة الطول
تُحسب بالبايتات لا بالمحارف — وهو ما يُنتج رمزًا غير قابل للمسح مع اسم
بائع عربي.

## قبل الإطلاق

ما كان ناقصًا صار مبنيًّا، وما بقي يحتاج **حسابات ومفاتيح** لا شيفرة:

- [x] **بوابة دفع** — طبقة مزوّدين كاملة في [`lib/payments/`](lib/payments/):
      `manual` (تحويل بنكي وتأكيد إداري) و`moyasar` و`tap` منفَّذتان مقابل
      واجهتيهما الموثَّقتين. لم تعد الطلبية تُسجَّل مدفوعةً من تلقاء نفسها.
- [x] **فوترة ZATCA** — المرحلة الأولى: فاتورة مبسّطة قابلة للطباعة مع رمز
      TLV مرمَّز base64 ([`lib/zatca.ts`](lib/zatca.ts))
- [x] **مهمة مجدولة** — [`/api/cron/sync-orders`](app/api/cron/sync-orders/route.ts)
      محميّة بـ `CRON_SECRET`، مع [`vercel.json`](vercel.json)
- [x] **سياسات معلنة** — الشحن والإرجاع والخصوصية والشروط في
      [`/policies`](app/policies/), وتنصّ صراحةً على أن نزاعات AliExpress
      تُدار يدويًا لأن فئة `aliexpress.issue.*` للبائعين لا للمشترين
- [x] **تأكيد البريد واستعادة كلمة المرور** — مُرسِل بثلاثة مزوّدين
      ([`lib/mail/`](lib/mail/)) وصفحتا `/forgot-password` و`/reset-password`
- [x] **تجديد رمز AliExpress** تلقائيًا ([`lib/aliexpress/token.ts`](lib/aliexpress/token.ts))
- [x] `try_to_pay` صار متغيّر بيئة (`AE_TRY_TO_PAY`) لا ثابتًا في الشيفرة

يبقى قبل الإطلاق:

- [ ] **حساب لدى مزوّد دفع** وضبط `PAYMENT_PROVIDER` ومفاتيحه و`PAYMENT_WEBHOOK_SECRET`
- [ ] **رقم ضريبي حقيقي** في `STORE_VAT_NUMBER` — الفاتورة ترفض الصدور بدونه
- [ ] **مُرسِل بريد حقيقي** (`MAIL_PROVIDER=smtp` أو `resend`) ثم تفعيل
      `AUTH_REQUIRE_EMAIL_VERIFICATION`
- [ ] **تفويض الحساب كدروبشيبينغ** ثم `AE_TRY_TO_PAY=true`
- [ ] **بروكسي عكسي** يضبط `X-Forwarded-For` ويُملأ به `TRUSTED_PROXIES`؛
      بدونه يُعطَّل تتبّع العنوان عمدًا ويسقط الخنق إلى مفتاح لا يُزوَّر
- [ ] **مخزن مشترك للخنق** (Redis) عند النشر بأكثر من نسخة —
      [`lib/rate-limit.ts`](lib/rate-limit.ts) في الذاكرة لكل نسخة
- [ ] مراجعة `DEFAULT_MARGIN_PERCENT` بحيث يستوعب المرتجعات وتقلّب الصرف
- [ ] ترقيم تسلسلي للفواتير — الرقم الحالي مشتقّ من رقم الطلبية العشوائي،
      وتتطلّب المرحلة الثانية من الفوترة تسلسلًا حقيقيًا

## مشاركة قاعدة البيانات مع مشروع آخر

يستخدم المشروع قاعدة بيانات مستقلة باسم `ae_ds_store` على مخطّط `public`،
فلا مشاركة ولا تصادم أسماء. لكن إن نقلته إلى قاعدة مشتركة وحمل رابط
الاتصال مخطّطًا مخصصًا:

```env
DATABASE_URL="postgresql://user:pass@localhost:5432/postgres?schema=nextstore"
```

فانتبه إلى مصيدة صامتة: **`?schema=` اصطلاح خاص بـ Prisma وبرنامج
تشغيل `pg` يتجاهله**. أداة الترحيل تحترمه فتُنشئ الجداول في المخطّط
المطلوب، بينما يستعلم وقت التشغيل في `public` ما لم يُمرَّر المخطّط
صراحةً إلى المُهيّئ. والنتيجة أخطر من مجرد فشل: إن شاركت القاعدة مع
مشروع آخر يحمل أسماء جداول مشابهة (`Order` · `Product` · `User`)
فستُقرأ بياناته وتُكتب فوقها بلا أي رسالة خطأ.

يعالج ذلك [`lib/db.ts`](lib/db.ts) بقراءة `?schema=` من الرابط وتمريره
إلى `PrismaPg`. ويتضمّن `verify:orders` فحصًا يثبت إصابة المخطّط الصحيح.
